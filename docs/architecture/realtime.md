# リアルタイム対戦設計

2026-08-30: COUNTDOWN、ホスト早期終了、誤回答通知、複数確定のACKは [操作・通信更新](interaction-update.md) に定義する。以下の初期案より同更新を優先する。

## 1. 部屋の単位

1部屋につき1つのDurable Objectを割り当てる。部屋内の参加、描画確定、回答、得点、時間切れを同じ場所で順番に処理し、競合を防ぐ。

## 2. ゲーム状態

```text
LOBBY
  └─ host starts ─> DRAWING
       ├─ all confirmed / timeout ─> ANSWERING
       └─ no valid differences ───> ROUND_RESULT (skipped)
ANSWERING
  └─ all found / timeout ─────────> ROUND_RESULT
ROUND_RESULT
  ├─ next stage ──────────────────> DRAWING
  └─ last stage ──────────────────> FINAL_RESULT
FINAL_RESULT
  ├─ rematch ─────────────────────> LOBBY
  └─ expiry ──────────────────────> DELETED
```

状態遷移はサーバーだけが確定する。イベントにはゲーム番号とステージ番号を含め、古い画面から届いた操作は拒否する。

## 3. 参加とホスト

- 部屋作成者を最初のホストとする。
- 参加順を単調増加する番号で保存する。
- ゲーム開始後は新規参加を拒否する。
- 切断した参加者の席は保持し、復帰を許可する。
- ホストが切断して30秒戻らない場合、接続中で参加順が最も早い人へ移譲する。
- 元ホストが戻っても、ホスト権限は自動的に戻さない。
- キックされた参加者の再接続情報は無効にする。

## 4. 接続と復帰

画面側はWebSocketを1本接続する。切断時は1秒、2秒、4秒、8秒、最大15秒の間隔で再接続する。再接続時に部屋ID、参加者ID、再接続情報、最後に受け取ったrevisionを送る。

復帰成功時は最新の完全な状態を返す。差分イベントだけに依存せず、スリープしたスマホでも画面を復元できるようにする。

## 5. イベント順序と重複防止

- サーバーイベントには部屋内で増加する`revision`を付ける。
- 画面側は現在値以下の`revision`を無視する。
- 変更操作には`commandId`を付け、再送時の二重処理を防ぐ。
- 回答はDurable Object内で受信順に判定し、最初の正解だけを確定する。

## 6. 時間管理

- 制限時間の基準はサーバー時刻とする。
- 開始イベントに終了予定時刻を含め、画面側は表示だけを行う。
- 終了処理にはDurable Objectのalarmを使う。
- 画面側のタイマーが0になっても独自に結果を確定しない。

## 7. 送信量の抑制

- 描画途中の共有は必須としない。最初の公開版では自分の端末にだけ描画し、確定時に線全体を送る。
- 将来途中経過を共有する場合、点を16〜33ミリ秒ごと、または一定数ごとにまとめて送る。
- 1イベント、1本の線、1ステージの最大サイズをサーバーで制限する。

## 8. 部屋の削除

| 状態 | 削除条件 |
| --- | --- |
| 未開始で全員退出 | 最後の退出から30分後 |
| 進行中で全員切断 | 最後の切断から2時間後 |
| 最終結果 | 最終結果へ移行してから2時間後 |
| 再試合開始 | 以前の削除予定を取り消して更新 |

期限はalarmとして保存する。接続または有効な操作があった場合、状態に応じて期限を再計算する。

## 9. 障害時

- 一部参加者の切断だけではゲームを止めない。
- 接続中が3人未満になっても進行中ステージは継続し、次へ進むかは結果画面でホストが判断する。
- サーバー再起動後は保存済み状態から復元する。
- 復元不能なら曖昧な状態で継続せず、全員へ終了理由を表示する。
