# 安全性・不正対策設計

## 1. 前提

ログインなしの友人向けゲームであり、完全な本人確認は行わない。その代わり、部屋外からの操作、入力の大量送信、ホスト権限の偽装、回答結果の改ざんをサーバー側で防ぐ。

## 2. 参加情報

- 内部roomIdと再接続用情報は暗号学的に十分な乱数で生成する。
- ルームコードだけでは操作できず、参加処理後に発行された部屋専用情報を必要とする。
- 再接続用情報は平文保存せず、サーバーではハッシュを保存する。
- URL、ログ、分析イベントへ秘密情報を含めない。
- キック時に該当セッションを無効化する。

## 3. 権限

- ホスト操作は毎回サーバー側の現在ホストIDと照合する。
- ゲーム開始、設定、キック、強制終了を画面表示だけで制御しない。
- 参加者は自分の描画だけ確定できる。
- 得点、発見済み状態、時間切れを画面から指定させない。

## 4. 入力制限

初期上限を以下とし、実測後に調整する。

| 対象 | 初期上限 |
| --- | --- |
| ニックネーム | 1〜20文字、制御文字禁止 |
| 1本の点数 | 2,000点 |
| 1ステージの線数/人 | 100本 |
| 描画確定データ | 256KB/人 |
| WebSocketメッセージ | 512KB |
| 回答送信 | 1人あたり毎秒5回、短時間の余裕あり |
| 部屋作成 | IP単位で制限 |

文字列はHTMLとして挿入せず、テキストとして表示する。座標の有限値、範囲、配列長、オブジェクト形状を共有スキーマで検証する。

## 5. 早押しと改ざん

- 正解領域は回答開始まで回答者へ送らない。
- 回答の正否と受付順はDurable Objectだけが決める。
- 画面の時刻や得点を信頼しない。
- commandIdとステージ番号で再送・古い回答を除外する。
- 推測連打を抑えるため送信頻度を制限し、将来は誤回答ペナルティも設定可能にする。

## 6. Webの基本対策

- HTTPSのみを使用する。
- Content-Security-Policy、X-Content-Type-Options、Referrer-Policyなどを設定する。
- 許可する接続元を本番ドメインと確認環境へ限定する。
- 依存関係の自動更新と脆弱性検査を行う。
- ソース、ログ、GitHub Actionsへ秘密鍵を保存しない。

## 7. ログ

requestId、イベント種別、匿名化した部屋ID、結果、処理時間、エラーコードを構造化ログへ出す。ニックネーム、再接続情報、Stroke全体、回答座標は通常ログへ出さない。
