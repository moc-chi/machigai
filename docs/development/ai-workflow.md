# AI駆動開発ルール

## 1. 目的

AIが要件確認から実装、テスト、Pull Request、確認環境への公開まで自律的に進め、人は重要な仕様判断と本番公開を承認する。

## 2. AIが担当すること

- 要件・設計書の更新
- 作業項目と受け入れ条件の作成
- 作業ブランチ作成
- 実装と必要な移行処理
- テスト追加と実行
- セキュリティ・差分レビュー
- Pull Request作成
- 確認環境への公開と動作確認
- 判断理由、残課題、戻し方の記録

## 3. 人の承認が必要なこと

- 本番公開
- 課金が発生するサービス変更
- 利用者データの収集範囲変更
- 認証、公開範囲、保存期間の変更
- 大きなゲームルール変更
- データを復元困難な形で削除する操作

## 4. 1作業の流れ

1. 関連する要件と設計を読む。
2. 目的、対象外、受け入れ条件をIssueへ書く。
3. 小さな作業ブランチを作る。
4. 先に失敗するテスト、または確認手順を用意する。
5. 最小の変更で実装する。
6. 単体、結合、ブラウザテストを実行する。
7. 設計判断が変わった場合は文書も更新する。
8. Pull Requestへ変更、確認結果、リスク、戻し方を書く。
9. 確認環境へ自動公開する。
10. 本番公開は人の承認後に行う。

## 5. Issueの必須項目

- 利用者が得る結果
- 背景
- 対象範囲と対象外
- 受け入れ条件
- 関連文書
- テスト観点
- 安全性・費用への影響

## 6. Pull Requestの必須項目

- 変更内容と理由
- 画面変更の確認方法
- 実行したテスト
- 未解決事項
- データや通信仕様への影響
- 戻し方
- 本番承認が必要か

## 7. AIが推測してよい範囲

既存設計内の命名、配置、小さなUI調整、テスト追加は合理的に判断して進めてよい。利用者データ、課金、権限、ゲーム結果、保存期間を変える判断は推測せず、人へ確認する。

## 8. 文書とコード

- 仕様変更は要件定義を更新する。
- 実装方式変更はarchitectureを更新する。
- 作業方法変更はdevelopmentを更新する。
- 未決定値を勝手に確定せず、設定値とTODOへ明示する。
- コメントは処理内容より「なぜ必要か」を記録する。
